# 下一轮卡顿优化方案（v21.19）

日期：2026-10-19。网站根目录 `D:/Vibe coding/作品集/docs`，测量对象为当前工作区（缓存标识 `cinematic-v21.18`）。本轮只做测量和方案，**没有修改网站源码**。所有改动的收益都在"内存补丁预览服务"里做了 A/B 实测：它读取真实的 `docs/`，只在内存中替换文本，不写盘。原始数据、脚本和对比图在本地忽略目录 `.workbuddy/perf-v22/`。

## 0. 结论

"卡顿"由三类问题叠加而成，按严重程度排序：

| # | 问题 | 实测（Intel Iris Xe，Chrome 155，ANGLE/D3D11） | 访客感受 |
|---|---|---|---|
| 1 | 着色器编译冻结 | 首次访问 173.5 s 后场景才就绪，主线程两次整块冻结（48.6 s + 59.5 s）。随后浏览一整轮，再累计冻结约 48 s：进入星图单段 16.2 s（最长一帧 7.9 s），飞向星域 13.8 s（最长一帧 6.8 s） | 页面"死机"、点击无响应 |
| 2 | 集显 GPU 过载 | 个人空间在完整画质下每帧 GPU 55–76 ms（13–20 fps）。自动画质降到最低档（DPR 0.62）也只有约 30 fps | 持续掉帧，画面发糊 |
| 3 | 帧节奏 | 60 fps 节拍器在 165 Hz 屏上按 3,3,3,2 个垂直同步出帧，帧间隔在 12.1 ms 和 18.2 ms 之间交替 | 匀速运镜时周期性顿挫 |

背景：这台电脑的 Chrome/Edge 都没有在 Windows"图形设置"里指定高性能 GPU。Chrome 实测 WebGL 跑在 Iris Xe 集显上，RTX 3070 闲置；Edge 走同样的 Windows 默认策略。多数访客也是集显或轻薄本，因此方案以集显为基准。

收益最大的两项已经实测验证：

- **体积着色器改为单一调用点**：冷启动从 173.5 s 降到 14.4 s，主线程冻结从 108 s 降到 5.8 s，画面计算不变。
- **画布去 AA + 透射降分辨率 + MSAA 分档**：个人空间每帧 GPU 下降 32%（折中配置）到 57%（激进配置）；星图从 87.7 ms 降到 35.9 ms。

## 1. 测量方法与边界

- 环境：无头 Chrome 155 + `--use-angle=d3d11`，实际渲染器为 `ANGLE (Intel, Intel(R) Iris(R) Xe Graphics (0x000046A6) Direct3D11)`，`EXT_disjoint_timer_query_webgl2` 可用。视口 1685×862 CSS px，DPR 1.5，接近主屏最大化窗口。冷启动测试每次都用全新的浏览器配置目录（无着色器缓存）。
- 工具（均在 `.workbuddy/perf-v22/scripts/`）：
  - WebGL 编译阻塞钩子：按程序统计主线程阻塞时间。
  - 逐 draw call 和逐帧的 GPU 计时器。
  - 程序缓存键差异分析：找出触发新着色器变体的参数。
  - 灯光清点、Chrome trace、CPU profile、整轮浏览脚本。
  - 内存补丁预览服务（`scripts/overlay/`）。
- 边界：
  - 只测了一台机器，没有测 RTX 3070 下的表现。
  - 无头模式没有真实显示器 vsync，帧节奏结论来自对现有节拍器代码的仿真。
  - 系统合成器（两块 165/180 Hz 屏）会占用同一块集显，基线 GPU 时间在 55–76 ms 之间波动，因此每组 A/B 都与相邻的基线比较。
  - 视觉判断只基于同机位截图，最终需要你目测确认。

## 2. 证据

### 2.1 首次访问：两个体积着色器各编译约一分钟

| 阶段 | 原版 | 单一调用点后 |
|---|---|---|
| 环境探针着色器 `compileAsync`（后台） | 60.8 s | 约 2 s |
| 探针渲染到立方体目标时的"线性输出"变体（同步） | 冻结 48.6 s | 冻结 2.5 s |
| 星云体积着色器在首帧同步编译 | 冻结 59.5 s | 冻结 2.8 s |
| 其余 64 个程序合计 | < 0.5 s | < 0.5 s |
| 场景就绪 | **173.5 s** | **14.4 s** |
| 同一浏览器配置再次打开（缓存命中） | 1.2–1.5 s | — |

单个着色器在新缓存下的编译实验（`compiletest.mjs`）：

| 星云体积着色器 | 编译时间 |
|---|---|
| 原版 | 51.4 s / 68.9 s（两次） |
| 循环内改用 `textureLod` | 68.9 s（无效） |
| `textureLod` + 内层循环动态上界 | 69.0 s（无效） |
| 6 路 `if/else` 改为"先选参数，只调用一次 `integrate()`" | **1.9 s** |
| 再加外层循环动态上界 | 1.7 s |
| 环境探针：原版 / 单一调用点 | 53.8 s / **1.8 s** |

根因：`immersive-nebula-pass.js:80-88` 和 `immersive-volume-field.js:223-231` 的 6 路分支各调用一次完整的步进函数。D3D 编译器（FXC）会把它内联 6 份，每份都含 34 步循环、每步多次 `field()` 采样和阴影探测，代码量暴涨。问题和 `textureLod`、循环上界无关。

Windows 上的 Chrome/Edge 都通过 ANGLE 把 WebGL 转成 D3D11 编译，Firefox 默认也使用 ANGLE，所以"所有浏览器都卡"。老访客命中缓存时只要约 1.5 s，但以下情况都会重新经历分钟级冻结：着色器源码有改动（每轮精修都会）、Chrome 或驱动升级、第一次来的访客。线上已提交的版本中，星云着色器同样是 6 路分支结构。

### 2.2 运行时变体重编译：每次切换场景都会再冻结

整轮浏览实测（`journey3.mjs`，全新配置，已带单一调用点和 GPU 补丁，只看编译）：

| 段 | 编译次数 | 主线程冻结合计 | 最长一帧 |
|---|---:|---:|---:|
| 序章航行 16 s | 24 | 9.0 s | 0.79 s |
| 欢迎场景 | 16 | 6.7 s | — |
| 个人空间·阅读 | 1 | 0.37 s | 0.40 s |
| 启航 → 星图 | 46 | 16.2 s | **7.9 s** |
| 航行 → 抵达 | 43 | 13.8 s | **6.8 s** |
| 扫描 → 信号 | 2 | 0.96 s | 0.60 s |
| 接近 → 停靠 | 4 | 1.2 s | 1.1 s |
| **合计** | **136** | **48.3 s** | |

通过比对程序缓存键（`keydiff.js`），确认了以下触发源：

1. **可见点光源数量变化**：随着模块加载，运行时灯光对象从 18 个增加到 27 个，散布在十余个模块中（观测站、档案、星港、舰船、驾驶舱、航门、行星等），通过父节点显隐来开关。可见点光数在 5–11 之间变动（例如 `numPointLights 7→9`、`9→7`、`8→6`）。点光数量是着色器宏，每变一次，所有受光材质都要生成新程序。
2. **环境探针尺寸随画质变化**：自动画质跌破 0.75 时，`immersive-lightstage.js:70` 把立方体从 128 切到 64，即 `envMapCubeUVHeight 512→256`，观测站 15 个材质整体重编译。欢迎场景那 6.7 s 就是这个原因。
3. **同一材质同时用于 InstancedMesh 和普通 Mesh**：共 7 个材质，最多的是 1 个实例网格加 23 个普通网格共用一个材质，会产生 `instancing 0↔1` 两套程序。
4. **懒加载资产的首次编译**：星港/舰队 GLB 的材质在首次可见时才同步编译，星图阶段 51 个，抵达阶段 57 个。
5. **镜像缩放物体**：个别物体触发 `flipSided` 变体（停靠阶段 4 个）。

每个 MeshPhysical 程序的片元着色器约 74 KB，在 D3D 下编译需 0.2–0.6 s；晶体 T 的变体需 0.9–1.4 s。

已排除的做法：把点光数补齐成固定 16 个，星图/航行的编译次数确实减半（46 → 22，43 → 10），但每个程序因为多算灯光而更重，总冻结只从约 48 s 降到约 46 s。正确做法是"少量固定灯位 + 预编译"，而不是简单补齐。

### 2.3 稳态 GPU：集显上每帧 55–76 ms

个人空间概览，完整画质（画布 1875×959，4×MSAA），逐 draw call GPU 计时（每帧中位数）：

| 部分 | ms/帧 |
|---|---:|
| 观测站（地面、舱体、T、屏） | 21.0 |
| ……其中地面（玄武岩 + 平面反射，每帧画两次） | 7.2 |
| 星云体积（670×343，32 步） | 7.7 |
| 作品展具 | 6.7 |
| 行星 Dawn / 星海 | 2.9 / 2.2 |
| 后处理（合成、输出、胶片、Bloom） | 约 4.6 |
| 平面反射（640×400） | 1.2 |
| 非 draw 开销（3 个多重采样 HalfFloat 目标的解析、透射 mipmap、清屏） | 约 15 |
| **合计（站点自带帧计时）** | **约 64** |

地面画两次是因为 r161 的透射机制：只要视野里有透射材质（T、压力屏、透镜），Three.js 就会把所有不透明物体再画一遍到一张离屏目标里。这张目标和绘制缓冲同尺寸，带 4×MSAA，HalfFloat 格式，还要生成 mipmap（`three.module.js:30094-30119`）。

A/B 结果（逐帧 GPU 中位数，`ab2.mjs`）：

| 配置 | 个人空间 GPU | 相对相邻基线 |
|---|---:|---:|
| 基线（仅编译修复） | 67.7 / 76.0 | — |
| 画布 `antialias:false, alpha:false` | 59.0 | −13% ~ −22% |
| 透射目标 0.5 倍、无 MSAA | 51.9 | −23% ~ −32% |
| 主场景和粒子层去掉 MSAA | 45.3 | −33% ~ −40% |
| 三项合并（激进） | **30.8** | **−54% ~ −59%** |
| 另一轮：基线 55.2 → 折中（2×MSAA、透射 0.75、画布无 AA） | **37.6** | **−32%** |
| 同一轮：激进配置 | 26.6 | −52% |
| 星图：基线 → 激进 | 87.7 → 35.9 | −59% |
| 序章入口：基线 → 激进 | 29.5 → 23.4 | −21% |

自动画质（访客的真实体验）：

- 基线：个人空间降到 q=0.56、DPR 0.62，约 30 fps。
- 激进配置：q 约 0.6–0.7，DPR 0.65–0.72；60 s 内 52.3 fps，只有 3 帧超过 34 ms。

视觉代价（`images/compare-aa.jpg`、`images/compare-balanced.jpg`）：

- 去掉 MSAA 后，显示屏外框的细高光变成虚线锯齿，T 的边缘变硬。
- 透射 0.5 倍时，T 内十字交汇处出现阶梯。
- 折中配置明显好于激进配置，但屏框仍有轻微虚线。

结论：抗锯齿必须按设备分档，并补一个后处理 AA；透射系数建议 0.75。

### 2.4 帧节奏

`immersive-frame-budget.js:3` 的节拍器固定按 60 fps 出帧。仿真结果（`pacersim.mjs`）：

| 刷新率 | 出帧节奏（以 vsync 计） | 帧间隔 |
|---|---|---|
| 60 / 120 / 180 / 240 Hz | 恒定（1 / 2 / 3 / 4） | 16.7 ms |
| 144 Hz | 3,2,3,2… | 13.6–21.1 ms |
| 165 Hz（这台笔记本的面板） | 3,3,3,2… | 11.9–18.5 ms |

导航按墙钟推进，所以每个显示帧的位移不均匀，表现为周期性顿挫。

自动画质只缩放 DPR（最低 0.56），每降一档都要重建全部渲染目标。在集显上，启动后约 20 s 内会连降多档。

### 2.5 CPU（在这台较快的笔记本上不是主瓶颈，但在普通办公本上会放大）

个人空间（激进配置，约 52 fps）下渲染主线程占用 37%，约 7 ms/帧。CPU profile 8 s 的热点：

- `getParameters` 383 ms、`getProgram` 206 ms、`setProgram` 172 ms、`getProgramCacheKey` 100 ms，合计约 0.86 s（约 10.5%）。主要来自 2.2 节第 3 点的共享实例材质：每帧都在两种模式之间重新取程序。
- `updateMatrixWorld` 261 ms。
- draw call 开销：391 次/帧，反射捕获帧 651 次。

- **首次进入**：103 个请求，约 11.2 MB。
  - 80 个 JS 模块，未压缩 2.16 MB。
  - 4 个字体，961 KB。
  - 2 个 GLB，5.6 MB。
  - 序章音乐 WAV，2.19 MB。

### 2.7 静态页面（直接浏览作品路径）

- 作品档案、案例页、关于我、诗集：首次绘制 0.12–0.38 s，滚动 p95 5.7 ms，基本健康。
- `/zh/work/` 冷访问时，水晶 T 的透射材质同步编译，造成一次 0.84 s 的长任务。为了显示一个 T，页面下载了 1.39 MB 的整座观测站 LOD 模型。
- 以上静态页数据测于当天 14:17，早于另一会话对作品档案的改动（14:51 起）。沉浸式引擎、three.js 和 immersive CSS 在本轮测量期间均未被改动。

### 2.8 已排查、本轮不需要改的

- **环境探针每 12 s 重捕获一次**：预热后单次 CPU 约 2 ms，60 s 内没有对应的掉帧。
- **DOM 绘制**：个人空间的 trace 中渲染进程 Paint/Layout 很少，瓶颈在 GPU，GPU 进程大量时间在等待 `Present`。`backdrop-filter` 在集显上仍有成本，但没有单独量化。

## 3. 方案

### P0-A 消除编译冻结（第一优先：收益最大、风险低）

**A1 体积着色器改为单一调用点（已验证）**

- 位置：`immersive-nebula-pass.js:80-88`、`immersive-volume-field.js:223-231`。
- 做法：分支里只挑选参数，每层循环只调用一次步进函数。外层循环可再改成由 uniform 推导的动态上界。

  ```glsl
  vec2 span;vec3 center,radii,tint,flowRate;float seed,extinction,sea;
  if(a.x<=nearest){span=a;center=uCenters[0];radii=uRadii[0];tint=uColors[0];seed=uSeeds[0];extinction=uExtinction[0];flowRate=uFlows[0];sea=0.;a=vec2(1e6,-1.);}
  else if(b.x<=nearest){/* 下标 1，其余同上 */}
  /* c、d、e 同上 */
  else{/* 下标 5 */sea=1.;f=vec2(1e6,-1.);}
  integrate(ray,span,center,radii,tint,seed,extinction,flowRate,sea,fog);
  ```

- 收益（实测）：冷启动 173.5 s → 14.4 s；单个着色器 51–69 s → 1.7–2.1 s。
- 回归：新增源码检查，确认两段 GLSL 中 `integrate(` / `stellarProbeLayer(` 的调用点各只有 1 处；现有体积数学测试保持通过。

**A2 剩余的同步编译改为后台预编译**

- 环境探针：`immersive-lightstage.js:97` 调用 `compileAsync` 时，先绑定一个线性 HalfFloat 渲染目标（与立方体目标同色彩空间）。否则正式捕获时会再同步编译一个"线性输出"变体：原版冻结 48.6 s，A1 之后仍有 2.5 s。
- 全屏 Pass：NebulaPass（体积 + 合成）、粒子合成、UnrealBloom 的各材质、OutputPass、胶片 ShaderPass、StarportOpticsPass、PMREM 内部材质。在 `prepareStartupShaders` 中用临时 Mesh 加上对应的渲染目标逐个 `compileAsync`，再沿用现有"逐程序让出主线程"的方式取 uniform。
- 预期：首访主线程冻结从 5.8 s 降到 0.3 s 以内（待实测）。

**A3 固定灯位（灯光池）**

- 建一个全局灯光池：方向光 2（key/rim，现已固定）+ 半球光 1 + 环境光 1 + **固定 N 个点光（建议 4）**。
- 各模块不再自己 `new PointLight`，而是在 update 时申请灯位，写入位置、颜色、强度、距离。不用的灯位把强度设为 0，但保持可见，不能靠显隐开关。
- 驾驶舱随相机的两盏灯、行星和舰船的远处点光，优先改成自发光或 lightstage 已有的 HDR 光卡。
- 收益：消除星图、航行阶段的主要重编译来源；同时减少每个 PBR 像素的光照循环次数，GPU 也会省。
- 风险：需要重新调光。
- 验证：整轮浏览时 `keydiff.js` 不再出现 `numPointLights` 变化。

**A4 环境探针尺寸固定**

- `immersive-lightstage.js:70` 的 `edge` 改为启动时按设备档位确定一次（建议固定 128），运行中不随自动画质变化。低档位改为减少 `uRadianceSteps` 或拉长捕获间隔。
- 收益：消除"自动画质跌破 0.75 → 15 个材质整体重编译"（实测欢迎场景 6.7 s）。

**A5 拆分实例化共享材质**

- 每个 InstancedMesh 使用独立材质：`clone` 一份，共享同一个 uniforms 对象和 `onBeforeCompile`。
- 镜像缩放的物体在导出时去掉负缩放，或改用单独材质并预编译。
- 收益：去掉 `instancing 0↔1` 变体；同时消除每帧的 `getProgram` 重算（2.5 节，约占主线程 10%）。

**A6 懒加载资产"先编译、后显示"**

- `ensureAssets()`（星港、舰队）、作品展具、阅读玻璃展具：GLB 解析完后立即执行 `renderer.compileAsync(root, camera, scene)`，覆盖主场景目标和反射目标两个变体。借助 `KHR_parallel_shader_compile`，编译在 GPU 进程后台进行。编译完成前保持不可见或继续用后备几何，尽量在启航动画（2.2 s）期间完成。
- 欢迎场景空闲时，用 `requestIdleCallback` 分片预编译个人空间四章和星图的材质。
- 收益：星图 51 个、抵达 57 个首次编译不再阻塞主线程。

**A7 收敛材质特性组合**

- 一次完整浏览后，`renderer.info.programs` 达到 256–298 个。同类陶瓷、金属统一参数组合；clearcoat、iridescence、transmission、sheen 只在确实需要的少数材质上开启。
- 目标：整轮浏览少于 100 个程序。编译总量和显存占用同步下降。

**A8 静态作品页的水晶 T**

- `international-static.js:661`：先 `compileAsync`，再画首帧。另外导出一个只含 T 的小 GLB。
- 预期：冷访问的 0.84 s 长任务降到 100 ms 以内，下载减少约 1.2 MB。
- 注：本轮测量期间，另一个会话已在修改作品档案，并生成了 `assets/models/tem-identity-v21.glb`（约 0.3 MB），方向与本项一致。实施时以该成果为准，补上 `compileAsync` 即可。

### P1-B 降低集显 GPU 负载

**B1 画布去掉 AA 和 alpha（实测 −13% ~ −22%）**

- `immersive-cosmos.js:40` 改为 `antialias:false, alpha:false`。所有内容都经后处理写入画布，最终 alpha 恒为 1，画布上的 4×MSAA 和透明合成完全是浪费。
- 需要目测的一点：首帧绘制前，画布会从"透明（露出 body 背景）"变成纯黑。

**B2 透射目标降分辨率、去掉 MSAA（实测 −23% ~ −32%）**

- Three.js 从 r172 起官方提供 `renderer.transmissionResolutionScale`。本项目固定在 r161，建议在 vendored `three.module.js` 做等价的两行回移植：第 30100 行的 `samples` 和第 30119 行的 `setSize` 乘以系数。同时更新 `manifest.json` 的 SHA256，并在 `scripts/vendor-three.mjs` 中以补丁形式记录这一改动。
- 系数建议 0.75（0.5 会让 T 内出现阶梯），并做成画质档位参数。

**B3 MSAA 分档 + 后处理抗锯齿（实测全去 MSAA 为 −33% ~ −40%）**

- 分档：
  - 高档（独显，或测得 GPU 有余量）：4×MSAA。
  - 中档（集显默认）：2×MSAA + 后处理 AA。
  - 低档：不开 MSAA + SMAA/FXAA。
- 需要新增 vendored 的 SMAAPass，或用 ShaderPass 实现 FXAA，放在 OutputPass 之后。
- 美术侧：屏框等亚像素级的细高光要加宽，或改用着色器边缘光。否则任何低采样方案下它都会闪烁、出现虚线。

**B4 重做画质阶梯，启动时直接定档**

- 启动时根据 `WEBGL_debug_renderer_info` 和前 60 帧实测的 GPU 时间确定档位，集显默认中档。
- 降档顺序：先降特性（MSAA → 透射系数 → 星云步数/分辨率 → 反射频率 → 阴影尺寸），最后才降 DPR。
- 档位切换只在镜头静止时生效，并限制切换频率。
- 档位切换不能改变着色器宏（与 A4 同一原则）。

**B5 星云体积降本（实测 4.8–7.7 ms/帧）**

- 现在体积每帧全量重算。建议隔帧或棋盘格更新并做重投影，因为星云本身是低频的。
- 或者在中档把像素上限从 230K 降到约 140K，步数从 32 降到 24。
- 预期节省 2.5–4 ms（待实测）。

**B6 地面材质（实测单次 3.1 ms，每帧画两次）**

- B2 之后，第二次绘制的成本降到约 0.25 倍。
- 再关闭地面的 clearcoat，反射采样从 5 次降到 3 次，受光的点光数量受 A3 约束。
- 预期再省 1.5–2.5 ms（待实测）。

**B7 合并展具 draw call**

- 个人空间每帧 391 次 draw，反射捕获帧 651 次，其中展具约有 383 次 Physical 和 249 次 Shader draw。
- 静态部件按材质合并（项目里已有 `consolidateHardware`，可推广使用）或改用 BatchedMesh。
- 隐藏章节的展具不参与反射捕获。

### P1-C 帧节奏

**C1 节拍器对齐垂直同步**

- 改造 `immersive-frame-budget.js` 的 `createRenderPacer`：用最近 rAF 间隔的中位数估计刷新率 R，取整数 n = round(R / 目标帧率)，每 n 个 vsync 渲染一帧。
  - 165 Hz：n=3，即 55 fps。
  - 144 Hz：n=2（72 fps）或 n=3（48 fps），取 GPU 能稳定维持的那个。
- GPU 跟不上时也要落在整数倍上（例如 165/4 ≈ 41 fps），而不是 3、2 交替。
- 验证：用 `pacersim.mjs` 确认各刷新率下出帧节奏恒定。

**C2 画质切换的时机**

- 画质切换避开运镜过程（现有逻辑已部分做到），切换后先预热一帧再显示。

### P2-D CPU

- **D1**：A5 顺带消除每帧的 `getProgram`/`getParameters` 重算。
- **D2**：静态物体（GLB 静态节点、展台）设置 `matrixAutoUpdate=false`。
- **D3**：反射捕获时跳过不可能出现在镜面中的根节点，减少 `traverseVisible`。
- **D4**：B7 的 draw call 合并同时降低 CPU 开销。

### P2-E 网络与资源

- **E1 音频压缩**：WAV 改为 Opus 或 AAC。18.8 MB 预计降到约 1.5 MB；首屏请求的序章音乐从 2.2 MB 降到约 150 KB。
- **E2 模型压缩**：GLB 用 gltfpack 做 meshopt 或 Draco 压缩，解码放到 worker。星港加舰队的 12.4 MB 预计可降到 2–4 MB。
- **E3 JS 加载**：80 个模块需要逐级发现。可以由 `build-international.mjs` 生成 `modulepreload` 列表，或引入可选的打包步骤。
- **E4 线上访问**：排查 `https://wqh-tempest.cn` 握手被重置的问题。GitHub Pages 不压缩 `.glb`，可考虑把模型和音频放到国内 CDN 或对象存储。

## 4. 实施顺序

1. **第 1 批**（低风险、收益最大，建议本轮完成）：A1、A2、A4、A5、B1、C1。
   - 预期：首访冻结从 108 s 降到 1 s 以内；集显 GPU 下降约 15%；165 Hz 下出帧匀速。
2. **第 2 批**：A3、A6、B2（系数 0.75）、B3（分档 + SMAA）、B4。
   - 预期：整轮浏览的编译冻结从 48 s 降到 2 s 以内；集显上个人空间在 DPR ≥ 0.8 时达到 50 fps 以上。
3. **第 3 批**：A7、B5、B6、B7、D、E。

每批完成后，都用同一套脚本重测并更新 QA 记录。

## 5. 验收标准

测试条件：本机 Iris Xe，Chrome 全新配置目录，窗口 1707×960、DPR 1.5。

- **冷启动**：本地场景就绪不超过 15 s，主线程单次阻塞不超过 200 ms，合计不超过 1 s。
- **整轮浏览**（`journey3.mjs`）：编译阻塞合计不超过 1 s，除首次资源下载外没有超过 200 ms 的帧。
- **稳态**（自动画质）：欢迎、个人空间、星图三个场景 p50 不低于 55 fps，p95 帧时间不超过 25 ms，DPR 不低于 0.8。
- **165 Hz**：渲染间隔恒为同一 vsync 倍数。
- **视觉**：同机位截图对比屏框、T 和地面反射，由你最终确认。
- **回归**：现有测试全部通过；新增检查项：GLSL 调用点数量、灯位数量恒定、PMREM 尺寸恒定、实例化材质不与普通网格共享。
